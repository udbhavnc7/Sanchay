# Sanchay — India UPI, Privacy, Security & Release-Compliance Specification

**Prepared:** 24 October 2026  
**Repository:** https://github.com/udbhavnc7/Sanchay  
**For:** Existing Sanchay codebase; implement incrementally, do not rewrite the app  
**Status:** Engineering guidance and compliance checklist, **not a legal opinion or regulatory approval**

> **IMPORTANT — THIS DOCUMENT SUPERSEDES `SANCHAY_REAL_P2P_UPI_IMPLEMENTATION.md` FOR RELEASE DECISIONS.** Do not ship or enable a general-purpose P2P `upi://pay` hand-off solely because the earlier technical specification describes how to construct it. First complete the payment-scope decision gate in Section 2 and obtain written confirmation where required. A valid URI is not proof that a particular product integration is permitted by NPCI, a PSP bank, Google Play, or applicable law.

---

## 1. Executive decision

Sanchay is presently described in its public README as a local-first personal-finance dashboard in an Android WebView. It stores dashboard records in `localStorage`, has simulated payee/payment flows, and states that no real bank, UPI, or card transfer occurs. The README also says that backups are manual JSON files and are not encrypted, and that the dashboard has not yet been verified on a physical Android device. Treat these as the current published baseline and confirm them in the current source and release artifact before changing functionality.

### Recommended product decision

**Build a compliant payment-recording and external-payment-assistance experience first; treat general P2P UPI deep-link launching as a gated capability, not an assumed entitlement.**

Sanchay must remain a personal-finance ledger unless the project deliberately enters a regulated payment-participant model. In the initial release, Sanchay must not hold, pool, route, receive, settle or safeguard money for users; create an in-app stored-value balance; collect credentials; act as a payment gateway/aggregator; or claim to be a bank or authorised UPI app.

There are three distinct levels of functionality:

| Path | What Sanchay does | Release decision |
|---|---|---|
| **Path A — payment assistance / record keeping** | Shows/copies the recipient's UPI ID and payment details, explains that the user must open their own trusted UPI app and complete the payment there, then allows them to record/reconcile the result in Sanchay. No UPI network API, no fund handling, no settlement claim. | **Recommended first shipping path**, subject to normal legal and Play review. |
| **Path B — prefilled P2P UPI intent/link/QR** | Builds a `upi://pay` URI or QR for a person-to-person payment and launches/shares it. The payer still authorises inside an external UPI app. | **Do not enable in a public release until the precise P2P use is reviewed and written confirmation is obtained from Indian payments counsel and, where applicable, NPCI/a sponsor or PSP bank.** NPCI's public material describes intent integrations in merchant contexts; it does not clearly establish that this specific generic P2P finance-tracker design is approved without TPAP onboarding. |
| **Path C — Sanchay participates as a UPI app / payment service** | Direct UPI network integration, native UPI onboarding, collection/transaction-status APIs, or Sanchay-originated payment requests/collect flows as a payment participant. | Only pursue after formal sponsor-bank/PSP relationship, NPCI onboarding/certification and approvals, security reviews, operating controls, grievance/dispute arrangements, and a legal review. Do not prototype production credentials or pretend to be onboarded. |

An external-app hand-off may be materially different from operating a payment system, but the exact classification depends on the functionality and operating model. The public sources below do not justify a blanket statement that any P2P UPI URI generated by any app is automatically approved or that a hand-off can never trigger other requirements. Resolve this explicitly before release.

## 2. Mandatory payment-scope decision gate

### Gate 0 — write down the operating model

Before coding a general P2P UPI integration, prepare a one-page flow diagram and answer all of the following:

- Does Sanchay only copy/share payment details, or does it generate a UPI URI/QR?
- Is the payee an individual, a merchant, or both?
- Does any payment-related API/SDK run inside Sanchay?
- Does Sanchay obtain transaction status from a bank/PSP, or does it rely on a callback or user confirmation?
- Does Sanchay ever receive, hold, pool, route, refund or settle funds?
- Does Sanchay create a UPI collect request/network message or only share a static payment request?
- Does the app receive any commission/fee or promote a third-party payment service?
- What payment data leaves the device, and which entity is responsible for a complaint?

### Gate 1 — written confirmation for Path B

Send the flow description and exact proposed intent/QR behaviour to qualified Indian payments counsel and the intended PSP/sponsor-bank contact; ask whether this particular **P2P, non-TPAP, local-first finance-app hand-off** is allowed, which NPCI circulars/specifications govern it, and what approvals/branding/Play declarations are required. Preserve their written response in the project’s compliance records.

If a PSP bank/NPCI says the flow requires TPAP onboarding, do not try to work around it by calling it a “link”, “shortcut”, or “external intent”. Either:

1. follow the formal TPAP route; or
2. ship Path A without prefilled UPI intent/QR.

If counsel believes no special UPI onboarding is required, still confirm the current NPCI/product-specific guidelines, Google Play declarations and design requirements before enabling Path B.

### Gate 2 — release authorisation

Path B must remain disabled in production builds until all of the following are recorded as complete:

- [ ] Payments-scope decision approved in writing.
- [ ] NPCI/PSP-bank requirements, if any, are met and evidence saved.
- [ ] Exact P2P hand-off/QR flow tested with compatible UPI apps on physical Android devices.
- [ ] Google Play Financial features declaration reviewed for the real feature set.
- [ ] Privacy policy, in-app disclosures, Data safety form, and support/dispute instructions match actual behaviour.
- [ ] Security review confirms no UPI PIN/OTP/bank credentials are collected or logged.
- [ ] Payment statuses cannot falsely claim success; duplicate ledger entries are prevented.
- [ ] Feature flag defaults to disabled in production until sign-off. Automated tests cover the disabled state.

Do not make release approval depend on a developer manually remembering these steps; enforce the gate in release configuration and CI/release checklist.

## 3. What official guidance says—and what it does not say

### RBI / Payment and Settlement Systems Act

RBI explains that payment-system operation in India is regulated under the Payment and Settlement Systems Act, 2007, and that a person generally cannot commence or operate a payment system without RBI authorisation. This does **not** by itself answer whether a particular app that only opens another regulated UPI app is operating a payment system; that is why the scope assessment in Section 2 is required.

Official source: [RBI — Payment and Settlement Systems Act, 2007 FAQ](https://www.rbi.org.in/CommonPerson/english/scripts/FAQs.aspx?Id=420)

### NPCI / UPI onboarding

NPCI's UPI FAQ states that an entity seeking to become a Third Party Application Provider (TPAP) should approach a sponsor bank to initiate onboarding. The same FAQ describes merchant UPI integration through an acquiring bank and lists QR, intent, application-based and collect modes for merchant integration. These merchant integration modes should not automatically be treated as permission for an unonboarded finance tracker to create arbitrary P2P flows.

Official sources (check current versions and circulars again before release):
- [NPCI — UPI FAQs](https://www.npci.org.in/what-we-do/upi/faqs)
- [NPCI — current UPI circulars list](https://www.npci.org.in/circulars/upi)
- [NPCI — Guide to Onboarding and Offboarding](https://www.npci.org.in/PDF/npci/others/Booklet-Onboarding-Offboarding.pdf)
- [NPCI — UPI product booklet](https://www.npci.org.in/PDF/npci/upi/Product-Booklet.pdf)

### Google Play

Google Play requires financial features to be declared in Play Console, including payment/transfer categories. Its policy lists “Mobile payments and digital wallets” and “Money transfer and wire services” among the declaration options. Decide the correct selection based on the actual shipped experience and get guidance from Play Console support if an external-app-only P2P hand-off is ambiguous. Do not declare “no financial features” once an actual transfer feature is present.

Google Play's UPI badge is distinct from merely creating a UPI URI. Google says apps may contact NPCI for eligibility/accreditation; do not show the official “Offers Payments through UPI” badge or claim NPCI accreditation without obtaining it.

Official sources:
- [Google Play — Financial services policy](https://support.google.com/googleplay/android-developer/answer/9876821)
- [Google Play — Financial features declaration](https://support.google.com/googleplay/android-developer/answer/13849271)
- [Google Play — Data safety and UPI badge information](https://support.google.com/googleplay/android-developer/answer/10787469)

### Important limitation

This specification is a careful engineering and release plan, not a substitute for written NPCI/PSP-bank confirmation or advice from a lawyer experienced in Indian payments regulation. No document written by an AI can certify Sanchay as “fully legal” without reviewing the final shipped app, operating entity, agreements, data flows and applicable current rules.

## 4. Safe initial product behaviour (Path A)

### Send money workflow

1. User selects a saved recipient and sees the exact UPI ID as **user-entered / not verified by Sanchay**.
2. Sanchay presents the entered amount, INR, optional note and a reminder to check the recipient name and amount in the trusted UPI app before authorising.
3. The initial version provides “Copy UPI ID” and “Copy amount/note” actions and instructions to open the user's installed UPI app and enter the information there. Do not generate a payment URI or QR in Path A.
4. Sanchay may create a local `payment_attempt` record with status `prepared` but must not record an expense yet.
5. After the user returns, they can choose “I paid”, “I cancelled/it failed”, or “I'm not sure”.
6. If they select “I paid”, the UI must say **“Marked paid by you — not verified by Sanchay”** unless a future authorised integration supplies trusted, independently verifiable evidence. Offer optional UTR/reference entry after the user checks their UPI app or bank history.
7. If outcome is unclear, leave it unresolved. Do not retry automatically or create an expense by default.
8. On user confirmation, add exactly one expense through the existing ledger/repository path. Link it to the attempt so confirming twice cannot create a duplicate. Do not separately decrement the balance if balances are derived from ledger transactions.

### Request money workflow

- Initial version may display/copy the user's own UPI ID and create a plain text request containing amount, note and instructions to pay using the payer's UPI app.
- Do not call this a UPI Collect request; it is merely a shared payment request created by Sanchay.
- Do not mark it paid because a message was shared or a QR/link was opened.
- Prefilled UPI URI and QR generation are Path B and remain disabled until the Section 2 gate is passed.

### Clear separation of three records

1. **External payment:** The payment occurs, if at all, inside the payer's selected bank/UPI provider.
2. **Sanchay payment attempt:** A local workflow record; it is not settlement proof.
3. **Sanchay ledger transaction:** The user's accounting record of the payment. It can be marked user-confirmed but must not be represented as bank-sourced unless it really is.

Do not imply Sanchay has a live bank balance or can reverse an external payment. Do not use status labels such as “Bank verified”, “UPI settled”, “Payment successful” or “Received” without an authoritative data source that actually supports that statement.

## 5. If Path B receives written approval: technical implementation requirements

This section is conditional. **It does not itself approve the integration.** If the Section 2 gate has not been passed, implement Path A only.

### URI construction and launch

- Follow the latest specifications supplied by the approved PSP/NPCI partner; do not treat an internet example of `upi://pay` as a normative protocol specification.
- Build the URI from validated typed fields, correctly encode every query parameter and reject unknown schemes/redirects.
- Restrict native launch code to an explicitly allowed UPI URI/action; never expose a generic `launchIntent(anyString)` bridge to JavaScript.
- Launch only after a user tap and a review screen; never initiate payment on page load, on import, from a notification, or in the background.
- Prefer the Android system resolver/chooser if allowed by the approved integration, handle missing UPI apps and launch errors, and test across multiple supported UPI apps on physical devices.
- Do not use `QUERY_ALL_PACKAGES` just to detect installed UPI apps. Use the narrowest Android package visibility/implicit-intent approach compatible with the approved design.
- Never capture/ask for the UPI PIN, OTP, bank password, card details or app authentication. Authentication happens only inside the payer's trusted UPI/banking app.
- Do not use SMS permissions, notification scraping, accessibility services or UI scraping to infer UPI payment success.
- Do not make a UPI response string alone equivalent to authoritative bank settlement.
- Never create a “collect” request or contact a UPI/network API unless this is specifically included in an approved participant/acquirer integration.

### Status handling

Use conservative states, for example:

`prepared -> handed_off -> needs_reconciliation -> marked_paid_by_user | cancelled_by_user | reported_failed_by_user`

If an approved provider integration later returns a signed/authoritative status, model that separately with the provider, source, timestamp and reference. Do not fabricate a UTR or provider transaction ID. “No response” is **unknown**, not success or failure. Never automatically retry an unknown transaction.

### P2P URI/QR verification

- Use official partner-provided parameters and conventions.
- Do not invent merchant-only fields or MCC/merchant identities for an individual.
- Do not attach a merchant label, official UPI logo/badge, or imply that a payee VPA has been verified.
- Treat user-entered VPA syntax validation as formatting only—not proof that the ID exists, belongs to the named person, or is safe.
- Test URI encoding for spaces, `&`, `?`, apostrophes, Kannada/Unicode and emoji; test invalid amounts and unsupported fields.

## 6. Payments safety and consumer protection requirements

- Always show the recipient's UPI ID and amount on a final review screen.
- Tell the user to independently verify the recipient name and amount within the UPI app before authorising.
- Never imply that scanning a QR or entering a UPI PIN is required to receive money. NPCI warns that entering a UPI PIN authorises a payment; it is not needed merely to receive money.
- Never auto-debit, auto-pay, schedule a UPI payment, use UPI AutoPay mandates, or run background transfers in this feature.
- Never retry an uncertain payment automatically. Doing so can cause duplicate transfers.
- No “reversal” or “refund” button that pretends Sanchay can reverse a bank transfer.
- Clearly explain: payment questions, pending debits, failed/reversed payments and unauthorised transfers must be handled through the payment app/PSP/bank and the applicable UPI dispute route. Sanchay can help correct its own local record but cannot reverse the bank transaction.
- For an external payment, do not charge an in-app fee or take a commission in the first version. Any monetisation tied to payments needs separate legal/partner/consumer disclosure review.
- Do not offer lending, credit, investment, banking or payment-aggregation services merely because the existing ledger has a loan-tracking screen or account labels. If the actual product starts connecting borrowers/lenders, advancing funds, holding money or providing financial products/advice, stop and conduct a separate regulatory assessment.
- Publish truthful Terms of Use and support contact details. Clearly state that balances and payment history are user-maintained records unless sourced from an authorised bank integration.

## 7. Privacy and data protection: treat as a release blocker

The current public README says dashboard data is stored in WebView `localStorage`, no dashboard data is uploaded/synced, and manual JSON backups are unencrypted. It separately identifies inherited Android modules and third-party SDKs. Do not assume that these statements establish what the final release APK sends over the network; inspect the complete Android manifest, Gradle dependencies, Firebase/Crashlytics configuration and production behaviour.

### Required release work

- [ ] Create a data-flow inventory covering the React dashboard, Kotlin bridge, Android permissions, native dependencies, Crashlytics/analytics, cloud/Firestore code, exports and backup flow.
- [ ] Check whether any financial data, VPA, payee name, transaction note, account balance or reference can enter logs, crash reports, analytics, clipboard history, notifications or support attachments. Remove or redact it where not essential.
- [ ] Audit the release APK on a clean device/network; document every outbound destination and payload. Do not promise “nothing leaves your phone” unless verified for the actual release build.
- [ ] Add a public privacy policy URL and an in-app Privacy page. Identify the developer, data types, purposes, local vs transmitted processing, third parties/SDKs, retention/deletion, user contact and complaint process. Make Google Play Data safety statements consistent with the actual SDKs and behaviour.
- [ ] Collect only data needed for a user-requested function. Do not collect contact lists, SMS, call logs, location, device IDs or banking credentials to support this feature.
- [ ] Add a secure data deletion/reset process and confirm it removes all applicable local copies, cached records and future cloud records if sync is added.
- [ ] Preserve local-first operation. No account or cloud sync should be added just to make an external UPI hand-off possible.
- [ ] Replace the unencrypted-backup assumption before a production finance app release: either provide a password-protected/encrypted backup with documented recovery or make the risks clear and do not describe backups as secure. Verify exports do not unintentionally include excessive sensitive data.
- [ ] Assess Android app-private storage and WebView hardening. Never enable permissive file access or a broad native bridge to make UPI work.
- [ ] Create a retention and incident-response procedure appropriate to the developer's actual operations and applicable law.

### DPDP timeline (as of 24 October 2026)

India's Digital Personal Data Protection Act, 2023 and the DPDP Rules, 2025 have phased commencement. The 13 November 2025 commencement notification provides that Rule 4 starts one year after publication, and the listed substantive Act provisions (including Sections 3–17) and Rules 3, 5–16, 22 and 23 start eighteen months after publication. On that schedule, those stages fall on **13 November 2026** and **13 May 2027**, respectively. Check for subsequent Gazette amendments/notifications before release. Do not incorrectly claim that every substantive DPDP duty is already in force today, and do not use the staggered timeline as a reason to delay privacy-by-design work.

Official sources:

- [MeitY — DPDP Rules, 2025 Gazette notification](https://www.meity.gov.in/static/uploads/2025/11/53450e6e5dc0bfa85ebd78686cadad39.pdf)
- [MeitY — commencement notification for the DPDP Act](https://www.meity.gov.in/static/uploads/2025/11/c56ceae6c383460ca69577428d36828b.pdf)

Counsel should assess the applicable IT Act/SPDI transition and any other current requirements for the final operating model.

## 9. Security engineering requirements

### Identity and access

- No Sanchay user-to-user cloud accounts are needed for Path A.
- Do not add a backend/payment server simply to create local payment attempts.
- If sync or accounts are introduced later, complete a separate threat model and authorisation design before implementation.

### Native/WebView bridge

- Expose narrow typed methods only; validate all arguments in Kotlin even if TypeScript validates them.
- Do not allow arbitrary JavaScript to launch arbitrary intents, read files, enumerate installed apps or invoke general native methods.
- Keep local trusted origin restrictions; do not weaken WebView settings for deep-link convenience.
- Do not place secrets in the React bundle, UPI URI, local logs or backups.

### Financial correctness

- Use the current ledger as the single source of truth.
- Model amounts as integer minor units (paise) or a verified decimal-safe type, with explicit currency and rounding rules.
- Use stable IDs; never use payee display name as a unique key.
- A payment attempt is not a transaction. Only one confirmed ledger entry should affect reports/budgets/balances.
- Add idempotency at the domain/repository boundary so retrying confirmation cannot duplicate expenses.
- Migrate the current local storage/backup schema without erasing users' existing data.
- Do not mark payment paid based on app return, a URI callback, a copied UPI ID, QR creation, share completion, or timeout.

### Logging, reporting and receipts

- Redact UPI IDs, recipient names, payment notes, local balances, UTRs and transaction-specific data from logs/analytics unless expressly necessary and properly disclosed.
- A local receipt must show the source and status accurately, for example **“Recorded in Sanchay; marked paid by you; not bank-verified.”**
- Never fabricate a bank transaction ID, UTR, reference, time or provider name.

## 11. Repository implementation plan

### Phase 0 — audit; do not code the payment hand-off yet

1. Inspect the actual `web/` payment/payee models, UI screens, payment handlers, transaction ledger, balance calculations, export/import code, tests, Android bridge and release configuration.
2. Trace where dashboard data is persisted. Confirm that no native Room code is silently assumed to share the WebView's `localStorage` ledger.
3. Inventory permissions, dependencies, SDKs, network destinations, Firebase/Crashlytics, any Firestore usage, logs and release build flags.
4. Reproduce the current simulated pay flow. Document which state changes today and make sure tests match reality.
5. Add no production payment API, backend, secret or SDK as part of this audit.

### Phase 1 — safe local payment assistance

1. Replace simulated success with explicit states: `prepared`, `needs_reconciliation`, `marked_paid_by_user`, `cancelled_or_failed`.
2. Add recipient UPI ID copy, amount/note copy, recipient details review and safe instructions to pay within the user's chosen UPI app manually.
3. Add receipt language which clearly distinguishes user confirmation from bank confirmation.
4. Link a marked-paid attempt to exactly one ordinary ledger expense using the existing transaction flow.
5. Add duplicate-confirmation guards, cancellation/unknown recovery, backup compatibility and migration tests.
6. Implement no UPI URI or QR in Path A.

### Phase 2 — compliance decision and gated implementation

1. Document and obtain written scope decision under Section 2.
2. If Path B is cleared, add the smallest possible native integration behind `UPI_P2P_INTENT_ENABLED`, default false in release configuration until required approvals are complete.
3. Verify URI parameter rules with the approving partner and test across installed UPI apps. If a formal participant integration is required, stop Path B and use the sponsor-bank/NPCI onboarding plan.
4. Complete Play declarations and privacy/security release items.

### Phase 3 — only with formal partnership, if desired

A true in-app UPI/TPAP experience is a separate product programme. Plan sponsor bank, NPCI onboarding/certification, partner requirements, security audits, user authentication, dispute and grievance operations, transaction status reconciliation, monitoring, incident handling, compliance ownership, data processing agreements and production support before writing integration code.

## 12. Required acceptance tests

### Path A

- [ ] User can copy the recipient UPI ID and payment details without launching any payment automatically.
- [ ] Wrong/empty UPI ID is not represented as verified.
- [ ] No UPI URI, QR, network collect request or UPI API is produced in Path A.
- [ ] A prepared or unresolved attempt never affects balances/reports as a confirmed expense.
- [ ] User-marked paid transaction is labelled “Marked paid by you — not verified by Sanchay”.
- [ ] Confirming the same attempt twice adds one ledger expense only.
- [ ] Cancelled/failed status adds no expense.
- [ ] Unknown state remains visible and does not auto-retry.
- [ ] UTR/reference entry is optional and clearly labelled user-entered unless sourced by an authorised provider.
- [ ] Existing transactions, budgets, reports, payees, export/import and backups still work.

### Path B (only after approval)

- [ ] Release feature flag stays disabled by default until sign-off.
- [ ] Tests cover URI encoding, Unicode, reserved characters, invalid amounts, unavailable handlers and activity-launch failures.
- [ ] The final review screen shows the exact recipient ID and amount.
- [ ] UPI return/callback alone does not create a bank-verified result.
- [ ] No SMS, notification, accessibility or app-screen scraping is used.
- [ ] All tested UPI apps are recorded in a compatibility matrix; unsupported cases show a fallback rather than a fake success.
- [ ] A physical Android device test has been completed for cold start/resume, cancellation, app kill, timeout and ambiguous return status.

### Release/legal checklist

- [ ] Written payment-scope review is stored in the repo's private compliance records; do not publish confidential bank/counsel correspondence.
- [ ] Play Financial features declaration is completed accurately.
- [ ] Privacy policy and Data safety declaration match the release APK and every SDK.
- [ ] No unauthorised UPI/NPCI logo, badge or affiliation claim.
- [ ] GPL-3.0 notices and source obligations are checked.
- [ ] Terms and support/dispute routing are published.
- [ ] A final independent review of security, privacy and payments compliance is complete before public production use.
